# EPIC 003.1 — daemon management

Status: **ready**. **Mandatory.** Multi-daemon support is not delivered until this epic ships.

EPIC 002 stores a registry of daemons and EPIC 003 proves one of them against `GET /v1/health`.
Neither adds a way to hold a second daemon: EPIC 003's connect screen edits **the selected daemon**,
so a human who types the VPS address over the local one replaces it. This epic makes the registry
reachable — name it, add another, switch, edit, remove — and shows which daemon the client is talking
to.

## Goal

- **G1** — `lib/features/daemon_connect/` gains a daemon list surface inside the settings `KDDialog`
  EPIC 003 built. It adds no route, and it adds no second feature directory.
- **G2** — The list shows every daemon by **name**, in the registry's insertion order, and marks the
  selected one. It shows the base URL as secondary text, so two daemons with the same name are still
  distinguishable.
- **G3** — Selecting a row calls `select(id)`. **The selection is by id, never by name and never by
  base URL**, so renaming a daemon or editing its address never re-points the selection.
- **G4** — Adding a daemon takes a name and a base URL, calls `add(name, baseUrl)`, and leaves the new
  daemon **unconfirmed and tokenless**. It does not select it, and it sends no request. The human
  selects it and proves it on the connect screen.
- **G5** — Editing a daemon changes `name` and `baseUrl` and keeps `id`. Editing the base URL clears
  `confirmedAt`, because a proven address is not evidence for a different address. The token is
  **kept**, because the operator often moves the same daemon.
- **G6** — Removing a daemon deletes its credential through EPIC 002 G6. Removing the selected daemon
  leaves the registry with **no selection** — a normal state — and the app renders it. It never
  silently selects a neighbour.
- **G7** — `KDTopBar` shows the active daemon: the name as `statusDetail`, and `KDConnectionStatus`
  from the selected daemon's last known outcome. Pressing it opens the settings dialog. `KDTopBar`
  already carries `status`, `statusDetail` and `onStatusPressed`, so this adds no `KD` component.
- **G8** — Every list row, control and empty state is a `KD` component. The feature defines no atom
  and hard-codes no design value.

## Non-goals

- No new route. The surface is the dialog EPIC 003 Story 07 already shows and, on `mobile`, the full
  screen `KDDialog` already renders below `600`.
- No new `KD` component. `KDCardList`, `KDCard`, `KDInputField`, `KDButton`, `KDDialog`,
  `KDStatusView` and `KDTopBar` cover every element.
- No probe. This epic never calls `GET /v1/health`. Proving a daemon stays the connect screen's job,
  and `confirmedAt` is written there.
- No import, no export and no sync of a daemon list. The human types each one.
- No per-daemon settings beyond `name`, `baseUrl` and the token. No per-daemon theme, no per-daemon
  polling cadence.
- No reordering and no sorting control. Insertion order is the order, fixed by EPIC 002 G3.
- No duplicate detection beyond G9 below.

## Rules the Stories must pin

- **Duplicate names are allowed.** `name` is a human label, `id` is the identity, and the base URL is
  shown on every row, so a duplicate is visible rather than ambiguous.
- **A duplicate base URL is allowed and warned.** Two entries pointing at one daemon is a mistake more
  often than an intent, and refusing it would block the legitimate case of two tokens for one address.
- **An empty name is refused.** The list has nothing to render, and the switcher is name-driven.
- **The base URL passes `isUsableBaseUrl`** — the rule EPIC 003 Story 03 already fixes — before `add`
  or `update` is called.
- **The cleartext warning of EPIC 003 G6 shows on the add form and the edit form**, not only on the
  connect screen.

Hermetic coverage required beyond the Proof:

- Renaming a daemon and editing its base URL leave `id` unchanged, and the selection still points at
  it.
- Editing the base URL clears `confirmedAt`; editing the name does not.
- Removing a non-selected daemon leaves the selection where it was.
- Removing the selected daemon leaves `selected()` null and renders the unselected state.
- A token saved for daemon A is unreadable after daemon A is removed, and daemon B's token is
  untouched.
- Adding a daemon issues no HTTP request. The test asserts an empty adapter request list.

`NEEDS-HUMAN:` two daemons, for real. Run a local daemon on `31415` and a second daemon on a VPS,
add both, switch between them in Chrome at `http://localhost:8080`, and prove each answers its own
`GET /v1/health` with its own token. **This one gates the epic**, because a registry of one proves
nothing about the capability. The VPS daemon needs its own
`KANTHORD_HTTP_ALLOWED_HOSTS` and `KANTHORD_HTTP_ALLOWED_ORIGINS`, and the cleartext warning must
show for it.

## Stories

- **The daemon list state** — the settings bloc or the dialog's own state: the daemon list, the
  selected id, and the add-versus-edit mode. A state is not a message.
- **The daemon list view** — `KDCardList` of `KDCardListItem`, one row per daemon, `highlightedId`
  bound to the selected id, name as title and base URL as description.
- **Select** — the row tap that calls `select(id)`, and the test that renaming does not move the
  selection.
- **Add** — the name field, the base URL field, `isUsableBaseUrl`, the empty-name refusal, the
  cleartext warning, and the assertion that nothing is probed and nothing is selected.
- **Edit and remove** — the edit form that keeps `id` and clears `confirmedAt` on a base URL change,
  and the removal that deletes the credential and can leave the registry unselected.
- **The active daemon in `KDTopBar`** — `statusDetail` is the daemon name, `status` is the last known
  `KDConnectionStatus`, and `onStatusPressed` opens the dialog.
- **The unselected state** — what the connect screen and the shell render when `selected()` is null.
  Never a crash, never a silent re-selection.
