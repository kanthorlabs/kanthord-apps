# EPIC 001.1 — the candidate client and daemon pinning

Status: **ready**.

An adjustment to EPIC 001, authored separately because `001-transport-foundation.md` is under active
implementation. It adds three things to `lib/api/`: a client that probes a configuration nobody has
committed yet, an endpoint identity that travels with the request, and a token read scoped to that
identity. Nothing here changes a resource method, a model or the exception envelope decoder.

It exists because two later decisions cannot be met by EPIC 001 as written:

- EPIC 003 G3 needs a probe against typed-but-unstored values while the registered client keeps
  serving the committed ones.
- The product supports more than one daemon, so the base URL and the token must be resolved from the
  **same** daemon for one request. Today `BaseUrlInterceptor` reads one provider and `AuthInterceptor`
  reads another, and a selection change between those two awaits sends daemon A's URL with daemon B's
  token.

## Goal

- **G1** — `lib/api/daemon_endpoint.dart` holds `DaemonEndpoint`: `id`, `name`, `baseUrl`. It is the
  SDK's identity for one daemon. `id` is opaque to the SDK and never parsed.
- **G2** — `BaseUrlProviderType` gains `Future<DaemonEndpoint?> endpoint()`. `baseUrl()` stays and
  keeps its EPIC 001 contract, so a static provider still satisfies both. `null` means no daemon is
  selected, which is a normal state and not an error.
- **G3** — `TokenProviderType` gains `Future<String?> tokenOf(String daemonId)`. `token()`, `save` and
  `clear` keep their EPIC 001 contract.
- **G4** — `BaseUrlInterceptor` resolves `endpoint()` **once** per request. It sets
  `options.baseUrl`, and it writes the id into `options.extra[kDaemonIdKey]`, where
  `kDaemonIdKey == 'kanthord.daemonId'`. A `null` endpoint throws `ApiNotConfiguredException` before
  the request leaves.
- **G5** — `AuthInterceptor` reads `options.extra[kDaemonIdKey]`. It calls `tokenOf(id)` when the key
  is present and `token()` when it is absent. Every other EPIC 001 G5 rule is unchanged: a null or
  empty token throws `ApiUnauthorizedException` before the request leaves, a `401` throws it again,
  and the stored token is never cleared.
- **G6** — `ApiException` gains one subclass, `ApiNotConfiguredException`. It means the client holds
  no daemon to call. It is never produced by a daemon answer.
- **G7** — `KanthordApi.withCandidate({required String baseUrl, required String token})` returns a new
  `KanthordApi` over a static endpoint and a static token. The candidate owns its own `Dio` and its
  own adapter, so `candidate.dio.close(force: true)` cannot disturb the client it came from.
- **G8** — `KanthordApi` takes `HttpClientAdapter Function()? adapterFactory`. It applies the factory
  to the `Dio` it builds and passes the factory to every candidate. This is the seam a test uses to
  put `MockHttpClientAdapter` under a candidate the feature creates internally.
- **G9** — `make arch-check` still passes. `lib/api/` imports no `features/`, `app/` or `libraries/`,
  and no `package:flutter/`.

## The pinning rule

One request resolves one daemon, one time, at the first interceptor. Every later stage reads the
pinned id and never re-resolves. EPIC 005 inherits the rule: a retry re-sends the request that
already carries `options.extra[kDaemonIdKey]`, so a retry can never migrate from a local daemon to a
remote one, and an idempotency key can never be replayed against a second daemon.

## The candidate contract

`withCandidate` **clones nothing**. It constructs a second `KanthordApi` through the ordinary
constructor:

- its own `Dio`, its own `HttpClientAdapter` from `adapterFactory` or the default;
- its own `ApiConfig` over a static endpoint whose `id` is `kCandidateDaemonId`;
- its own interceptor pair, built by the constructor.

Two consequences are binding and must be stated in the SDK README:

- **Every interceptor a candidate needs is added by the `KanthordApi` constructor.** EPIC 005 adds
  retry, idempotency and logging there, never onto a `Dio` from outside, or a candidate probes with a
  different stack than the client it came from.
- **The caller owns the candidate and closes it.** Nothing else holds a reference.

## Non-goals

- No `KanthordApiType` and no `SystemResourceType`. Both classes stay `final`. A second client
  implementation does not exist, and a transport change is an `HttpClientAdapter` swap under the
  existing `Dio? dio` parameter.
- No registry, no persistence and no selection logic. `lib/api/` reads a provider and never decides
  which daemon is selected. EPIC 002 owns that.
- No retry, no idempotency, no logging. EPIC 005 owns each.
- No change to `SystemResource`, to any model, or to `ApiException.fromDio`'s envelope decoding.

Hermetic coverage required beyond the Proof:

- A request carries the resolved id in `options.extra`, and the token the request sends is the token
  of **that** id, proved with a selection that changes between the two interceptors.
- Closing a candidate leaves the parent client able to issue a further request.
- A parent and a candidate issue concurrent requests without interference.
- A candidate built from a parent that carries `adapterFactory` answers from that adapter.

## Stories

- **`DaemonEndpoint`** — the three fields, `==` and `hashCode`. No JSON. Persistence is EPIC 002.
- **The two provider contracts** — `endpoint()` on `BaseUrlProviderType`, `tokenOf(id)` on
  `TokenProviderType`, and the static implementations `withCandidate` needs.
- **`ApiNotConfiguredException`** — the subclass, its place in the sealed hierarchy, and the
  assertion that `fromDio` never returns it.
- **The pinning interceptors** — `BaseUrlInterceptor` writes `kDaemonIdKey`; `AuthInterceptor` reads
  it and falls back to `token()` when it is absent. The test drives a provider whose selection
  changes between the two awaits and proves the pair never mixes.
- **`withCandidate` and `adapterFactory`** — the constructor parameter, the candidate construction,
  the ownership rule, and the three lifetime tests.
- **`lib/api/README.md`** — the resource table plus the two binding rules of the candidate contract.
